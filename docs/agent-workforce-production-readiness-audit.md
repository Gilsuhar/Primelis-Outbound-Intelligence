## Architecture findings and retained safeguards

- **Authentication:** request-scoped Supabase clients, Google PKCE cookies, server `getUser()` verification, preapproved application User records and database roles. JWT user-editable metadata never grants application roles. Middleware signature checks are not the final application authorization. Cross-user run/evidence SQL predicates retain `userId`.
- **CRM intake:** fixed owner `1087915602`; created/owner-assignment evidence and stable HubSpot Record ID. Lastmodifieddate is discovery input, not proof of assignment. Keyset pagination, per-contact association pagination, refresh queues and watermarks remain separate. Partial pages never clear eligibility.
- **Outreach:** OAuth refresh grants are actor-bound AES-256-GCM encrypted and rotated under a PostgreSQL advisory transaction lock. Possibly consumed grants are not automatically replayed. A database commit failure during grant rotation can require administrator reauthorization. No authorization-code callback is provided by this application; administrator bootstrap remains required.
- **Verification:** ZeroBounce email adapter and authorized verification-gateway adapter are real transport code; no gateway service or employment data license is supplied. Email identity/source/edit time is bound into proof. Catch-all, stale, unknown or mismatched proof is HOLD; Boring green is insufficient. Role title does not establish Search remit.
- **Eligibility:** deterministic threshold/seniority/Search, suppression, four-calendar-month cooldown, authority and freshness checks. Missing complaint/retention/all-user visibility cannot become CLEAR. Research is permitted for appropriate HOLD contacts, independently of draft readiness.
- **Research:** OpenAI live discovery followed by permitted public HTTPS content retrieval, DNS/IP pinning, exact-quote attribution and independent grounding review. Pages are untrusted data. Social/login-only sources and private/network addresses are rejected. Workspace proxy restrictions are never bypassed.
- **Similarweb:** no licensed adapter is connected. Only DATA_UNAVAILABLE with empty metrics; no invented estimates. Optional for a first sourced research run.
- **SERP:** optional authorized SerpApi snapshot with query/location/country/device/time/source. A single snapshot is not sustained competitor activity or first-party CPC/savings evidence. Capture recommendations refer to actual observations; screenshots are not fabricated.
- **Drafts:** actual structured OpenAI strategy/writing/quality modules; four distinct touches, creative alternatives, source and claim IDs, bounded revision, approved product wording only. Deterministic identity/citation/numeric checks plus a separate LLM critic remain in force. Live naturalness/commercial quality still needs human evaluation; mocked text cannot certify it.
- **Approval:** human content review remains separate from contact eligibility. Fresh identity, history, employment/email, approved knowledge or evidence changes invalidate affected approvals. Neither human review nor automation enables `canSend` or `canEnroll`.
- **Jobs/costs:** per-operator transactional state, versioned model runs, fenced leases, retry checkpoints, rate-limit backoff, failed-contact queue, local-day idempotency and Jerusalem DST handling. Estimated reservations happen before paid calls, including manual routes. Failed/uncertain attempts retain conservative charges, not fictional provider bills. Ordinary unpaid CRM/page reads use existing bounds, rather than paid-cost reservations.
- **Scale/maintenance:** daily reports/ledger reuse existing bounded JSON state rather than a new broker. This is a single-operator implementation, not a large multi-tenant queue. Legacy deterministic drafting/research helpers remain for legacy routes; operational Draft Studio uses real model adapters. No template fallback is substituted for a failed live provider.

## Database readiness

Ten existing migration SQL files were inspected in filename order and replayed successfully on PostgreSQL 16 in network-disabled Docker containers containing only fictional data. None contains DROP, DELETE, TRUNCATE or dropped-column/constraint operations. A second catalog was generated from the current Prisma schema and compared: table columns/types, enums and indexes are present. Column order is immaterial. Five existing array columns have intentionally stronger migration constraints/defaults than Prisma's generated SQL: three AccountAssessment arrays are NOT NULL, and GeneratedDraft `retrievedKnowledgeIds` / `sourceIds` are NOT NULL with empty-array defaults. These were preserved; no data constraint was weakened to make an automatic diff empty.

A separate upgrade database seeded with a pre-existing fictional User and legacy GeneratedDraft before subsequent migrations retained both records, with the new auth binding initially null. Actual Prisma store tests exercised append/read, cross-user isolation, optimistic version rejection, concurrent estimated-budget admission, concurrent daily start and the model-stage advisory lease and approved knowledge/source SQL joins through a workspace Unix socket. This is real local PostgreSQL validation, **not Preview connectivity, live migration status or proof of compatibility with every existing row**.

`IntegrationState` and `IntegrationAuditEvent` have RLS enabled without public policies; server Prisma needs the trusted server database role. Older application tables do not all enable RLS in the migration chain. On the isolated Preview project, the administrator must inspect effective Data API grants/RLS on User, Prospect, ProspectSource, GeneratedDraft and knowledge/source tables. Do not assume that application API authentication protects a separately exposed Supabase Data API. Never resolve permissions by granting anon/authenticated access to private tables. Actual deployed grants and public-schema exposure could not be inspected.

**Deployment procedure:** first create/verify a dedicated Preview database/project or independently isolated database/schema with a separate server role. Bind Preview-only `DATABASE_URL` and `DIRECT_URL`; leave Production bindings unchanged. Verify database name/role and backups in the trusted platform console, then run `prisma migrate status` against that reviewed target. Resolve existing baselines/history deliberately; do not blindly replay initial SQL against populated tables. Apply pending migrations with `prisma migrate deploy` only after the isolated target and its backup have been checked. Do not use migrate reset or db push. No migration is run during application startup.

**Recovery:** retain encrypted-grant database backups and the independent encryption key. On a failed migration, inspect `_prisma_migrations` and the exact failure; investigate and restore an isolated backup/clone or prepare a reviewed forward fix. Do not auto-mark a migration applied, edit previously applied SQL, delete the migration table, or run a destructive down migration. Roll back application code to a compatible Preview revision while preserving database evidence. A lost/possibly consumed Outreach refresh grant requires reauthorization, not repeated guessed refreshes.
